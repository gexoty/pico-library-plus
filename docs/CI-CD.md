# GitHub Actions и публикация

Workflow: .github/workflows/release.yml. Используется существующая Python/Apktool-сборка, без переноса на Gradle. Ubuntu 24.04, JDK 21, Python 3.13, SDK Platform 34, Build Tools 36.0.0. Сторонние Actions закреплены полными commit SHA. Apktool загружается с проверкой SHA256. input/original.apk и vendor/shizuku должны входить в будущий коммит: без них сборка намеренно завершается ошибкой. Исходный APK содержит сторонний код; права на распространение необходимо учитывать согласно NOTICE.md.

Push / Pull Request запускают тесты, сборку и проверку обоих APK и модуля, сохраняют Artifacts без публикации. workflow_dispatch делает то же самое. Теги vMAJOR.MINOR.PATCH должны точно совпадать с VERSION; неправильный тег останавливает сборку.

По уточнению пользователя все APK подписываются стандартным Android debug-ключом. ANDROID_KEYSTORE_BASE64, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_ALIAS, ANDROID_KEY_PASSWORD настраивать не требуется. Приватный ключ не входит в репозиторий или Artifacts. ~/.android/debug.keystore сохраняется через Actions Cache с ключом picolibrary-standard-debug-key-v1. Оба APK используют один сертификат. Кеш может быть удалён GitHub: тогда генерируется другой debug-сертификат, и обновление установленного APK с прежней подписью будет несовместимо. Для гарантированной долговременной идентичности понадобится отдельно согласованное постоянное хранение ключа. Локальный и CI debug-ключи также могут различаться.

Публикация включена для тегов после успешной проверки сборки. Дополнительная переменная разрешения не требуется. Порядок первого запуска:

1. Самостоятельно создать GitHub-репозиторий и отправить подготовленные файлы (этот этап локальной работой не выполнен).
2. Запустить Actions → Build and release → Run workflow. Скачать verified-picolibrary и проверить артефакты. Эти APK проверены на хосте, а не на шлеме.
3. При необходимости настроить GitHub Environment release и reviewer. Переменная разрешения публикации не требуется.
4. Изменить VERSION, сохранить изменения в коммите, затем создать и отправить соответствующий тег, например v1.0.0.
5. Успешная проверка тега допускает отдельный publish job. Он скачивает артефакты этого же запуска, проверяет контрольные суммы и тип подписи, создаёт Release с standalone APK, Magisk ZIP и SHA256SUMS.txt.

GITHUB_TOKEN имеет contents:read для сборки; contents:write выдаётся только отдельному publish job. PR не получает публикацию, release-ключи не нужны. Push веток, Pull Request и ручной запуск создают Artifacts без Release. Повторное создание существующего Release завершается отказом без перезаписи его файлов. Workflow не запускался на GitHub в рамках локальной задачи.
